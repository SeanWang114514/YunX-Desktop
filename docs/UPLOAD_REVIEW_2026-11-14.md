## 并发静态核查

- 调度器按配置扣除活动数量，为多个不同名文件分别在 `Dispatchers.IO` 启动任务，各项拥有独立 UploadIo、进度及速度采样。
- 上传会话锁按网盘批次互斥，不在整段文件传输期间持锁。HttpClients 的同步区仅覆盖客户端缓存构造，不覆盖 HTTP 请求。
- UploadIo 的请求使用同步 `execute()`。未发现经异步请求队列串行发送整个上传文件的实现；没有为此修改 OkHttp Dispatcher 参数。
- 已查阅十个平台上传入口及分片逻辑，未发现把不同名文件强制放到同一个全局传输锁中的代码。单个文件内部仍按平台协议顺序上传分片。
- 并发上限保持可配置 1–10、默认 3。调高触发补位；调低不取消已运行项。文件数量不足、同名文件、哈希准备和等待网盘确认会使实际传输数低于上限。

这些结论仅来自源码检查，不代表已复现用户报告的串行现象，也不代表真实账号已达到特定并发或速度。

## 失败、重试及边界

普通失败不再被写成全批停止错误。最终汇总仍保留首个失败原因，每项也保留自己的原因。已知账号错误停止后续派发；不能明确分类的平台错误按文件失败处理，不根据模糊文字或所有 HTTP 403 猜测账号失效。

结果在内存中按平台保留最近一个失败/取消批次，关闭结果或启动新批次后清除。重试只包含失败项，不包含已完成或取消项；不会自动重试整批写操作。重试会重新读取本地文件，不是分片断点续传。退出应用后不保留队列。

如果上次上传已在服务端保存、仅确认响应丢失，再次上传仍可能产生重复文件，用户可以在重试前刷新检查目标目录。失败和取消项的剩余字节不再计入整批 ETA；停滞文件存在时 ETA 显示占位符，避免使用其他文件的速度掩盖等待。

安装身份与通知身份已区分，但仍沿用原数据目录和单实例机制；没有迁移数据库或支持原版、修改版同时运行。便携启动器继续使用 `YunX-Desktop.exe` 和原内部配置名。
